# Spotify → Discord без Jam, с аудиодвижком LavaPlayer

Это обновление добавляет `/listen start`, `/listen stop`, `/listen status`, `/listen queue`, `/listen source`. Команды `/jam` оставлены для совместимости с существующим локальным плеером. Для `/listen` Spotify Jam создавать не нужно.

## Как работает

- Каждый пользователь авторизует и подтверждает **свой** Spotify Premium. Источник сессии — аккаунт того, кто вызвал `/listen start`.
- Бот опрашивает текущее воспроизведение и доступную очередь `/me/player/queue` по умолчанию раз в 5 секунд. Полного атомарного снимка и push-событий Spotify не предоставляет: при смене композиции несогласованный снимок временно помечается как обновляющийся.
- На одной редактируемой панели показываются текущий трек, обложка, прогресс и первые пять доступных песен «Далее». Порядок и намеренные повторы Spotify сохраняются. Неудачный запрос очереди обозначается ошибкой, а не пустой успешной очередью.
- Spotify продолжает управлять переходами, паузой, продолжением и позицией. Бот следует **текущей** композиции; он не проигрывает устаревший список автономно после потери доступа к Spotify.
- Источник звука — отдельный компактный Java-сервис на LavaPlayer, с YouTube/SoundCloud-модулями того же семейства, которое использует [jagrosh/MusicBot](https://github.com/jagrosh/MusicBot). Это не запуск второго Discord-бота. Java декодирует поток в PCM на loopback, Node.js кодирует Opus и отправляет его через уже проверенное Discord Voice/DAVE-соединение.
- **Новая песня требует первого подтверждения источника.** Нажмите «Выбрать источник», откройте ссылки, проверьте именно ту же запись/версию и право её трансляции, затем выберите. Разрешение сохраняется отдельно для вашего Discord-пользователя и Spotify track ID. Последующие включения этого трека используют подтверждённый источник автоматически. Неверный/недоступный источник не заменяется первым случайным результатом.
- Длительность используется как фильтр поиска, а не доказательство совпадения. При заметном изменении метаданных подтверждённого источника бот останавливает звук и просит подтвердить снова. Пауза/seek учитываются с задержкой опроса и загрузки.

Публичная доступность ролика, Premium или наличие платформы в MusicBot **не предоставляют права на трансляцию**. Подтверждайте только контент, который вы можете воспроизводить таким способом, с учётом условий источника. Подтверждение — заявление пользователя, а не автоматическая юридическая проверка. DRM, возрастные/региональные ограничения, вход и проверки «не робот» не обходятся. Источник может отказать серверному IP; соответствующая ошибка возвращается явно. В таком случае нельзя обещать воспроизведение любой песни.

## Установка на текущий Wispbyte

1. Остановите сервер. Сохраните закрытую резервную копию `.env` и `data/`.
2. Загрузите `lfgmusic-listen-engine-update.zip` и распакуйте **в `/home/container`**, разрешив замену файлов. Нужны все включённые части: `src`, `dist/src`, `scripts`, `audio-engine` и `bin/jre`. Они не должны оказаться во вложенной папке. Архив не содержит `.env`, SQLite, ваших аудиофайлов или токенов. Существующий cloudflared и `media/` сохраняются.
3. Добавьте в существующий `.env`:

   ```dotenv
   MUSIC_ENGINE_ENABLED=1
   MUSIC_ENGINE_SOURCE=youtube
   MUSIC_ENGINE_PORT=2334
   MUSIC_ENGINE_MAX_STREAMS=1
   ```

   Другие значения, Spotify/Discord-ключи, HTTP_PORT, домен и TOKEN_ENCRYPTION_KEY не меняйте. `2334` — внутренний loopback-порт аудиосервиса; не открывайте его в Cloudflare или наружу. Общий секрет между Node и Java генерируется launcher автоматически и не выводится в журнал. Новые Spotify/YouTube-пароли не нужны.
4. На один запуск установите Startup Command:

   ```bash
   cd /home/container && node dist/src/register.js && node scripts/start-with-tunnel.mjs
   ```

   Будет зарегистрировано 7 верхнеуровневых команд, включая `/listen`.
5. Запустите сервер. Ожидаются строки `[audio-runtime]`, `[audio-engine] loopback service ready`, подключение туннеля и `Discord подключён`. Если Java/JAR отсутствует или checksum не совпадает, процесс остановится с точной причиной; не меняйте ожидаемый hash, чтобы обойти ошибку, — загрузите правильный пакет целиком.
6. Для дальнейших рестартов верните обычную команду:

   ```bash
   cd /home/container && node scripts/start-with-tunnel.mjs
   ```

7. В Discord завершите старый тестовый плеер `/jam stop`. Войдите в voice-канал, включите Spotify и вызовите `/listen start`.
8. На панели нажмите **«Выбрать источник»** либо выполните `/listen source`. Только владелец Spotify-сессии может выбрать источник; сообщение с результатами видно ему одному. Откройте предложенные ссылки, проверьте запись/разрешение и выберите нужную.
9. Проверяйте переключение Spotify, паузу, продолжение и перемещение по позиции. Для другой новой песни снова подтвердите источник; для уже подтверждённых выбор хранится. Изменения «Далее» автоматически отображаются, но аудио стартует только когда Spotify действительно переключит текущий трек.

Повторный Spotify login не требуется, если ваша Premium-привязка уже подтверждена. При смене приложения/учётной записи учитывайте прежние инструкции OAuth. Ошибки загрузки источника вызывают паузу повторов на 30 секунд, чтобы не отправлять запрос на каждом тике. Новый подтверждённый источник сбрасывает эту паузу. Источники и привязки пользователей не подменяют друг друга. `/spotify logout` также удаляет выборы аудио этого пользователя. На одном Discord-сервере остаётся одна активная сессия.

## Память и ограничения тарифа

- Комплект предназначен для Linux x64, как в показанном Wispbyte-образе. Temurin JRE 21.0.13+9 включён; sudo/systemd и системная установка Java не требуются.
- Java запускается с ограничением heap 96 МБ, ограничениями direct memory/metaspace/code cache и Serial GC. В реальном тесте двух декодирований процесс занял около 71 МиБ RSS. Это **не** пик памяти поиска YouTube, всех пользователей или полная нагрузка Wispbyte.
- При известном cgroup-лимите ниже 384 МиБ launcher отказывается запускать дополнительный движок. Для 512 МиБ предлагается начать с **одного** аудиопотока; работа при пиковой нагрузке и лимитах CPU требует проверки на вашем тарифе. Дополнительные серверы могут читать Spotify, но второй одновременно звучащий поток при `MAX_STREAMS=1` получит явную ошибку лимита.
- Если ресурсов недостаточно, установите `MUSIC_ENGINE_ENABLED=0` и перезапустите: прежний локальный каталог и тестовый сигнал продолжат работать. Для нескольких одновременных внешних потоков понадобится больше ресурсов; не увеличивайте лимиты вслепую.
- Если YouTube ограничивает доступ с IP, можно выбрать `MUSIC_ENGINE_SOURCE=soundcloud` и перезапустить для поиска в другом поддерживаемом источнике. Это не гарантия наличия нужной записи. Требование входа/проверки не обходится.

## Безопасность и восстановление

Java слушает только `127.0.0.1`, каждый запрос проверяет секретный заголовок. Spotify/Discord-токены в Java не передаются. Нельзя передать произвольный URL/файл в качестве аудио: `/load` принимает только поддерживаемые HTTPS-домены, поиск использует фиксированные источники, плейлисты и прямые файловые пути снаружи не поддерживаются. Тестовый локальный файл доступен сервису только при специальной переменной интеграционного теста, которая launcher в production не передаёт.

Бот хранит зашифрованные выборы источников по Discord user ID и Spotify track ID, а не общий аккаунт для всех. Кнопки одноразовые, привязаны к текущему треку и живут 10 минут; при смене трека старое подтверждение отклоняется. После перезапуска сервис заново получает поток по сохранённому публичному URL. Закрытые CDN-ссылки, voice/Spotify-токены и PCM не сохраняются в базе. Никакие новые секреты не нужно отправлять в чат.

Launcher управляет Java, cloudflared и Node совместно. При падении одного завершает остальные, чтобы не оставить ложный статус работающего сервиса. При остановке голосовой поток закрывается, Java освобождает декодер, Node сохраняет сессию.

## Проверки и происхождение

Проверены сборка Java/TypeScript, 39 автоматических тестов, реальный путь Java → HTTP PCM 48 кГц/stereo → Node voice Opus, частота и длительность сигнала, seek, loopback-аутентификация, Premium/личные привязки, источник только после подтверждения, устаревшие кнопки, изменения очереди/треков и отказ без подстановки неверной записи. Поиск и воспроизведение публичных YouTube/SoundCloud-записей **с IP вашего Wispbyte** требуют отдельной проверки после установки; эта среда не доказывает их доступность.

Используются LavaPlayer 2.2.1 и YouTube source 1.5.2 — версии из исследованного MusicBot. YouTube-модуль собран из официального тега `5b2c08ab16b5af86755a660be92ceb7dd81bffde`, common + v2 overrides, с upstream LICENSE. Его Maven-хост был недоступен из среды сборки, поэтому использованы официальные исходники GitHub, а не непроверенный бинарник. Остальные зависимости получены по HTTPS с checksumPolicy=fail из Maven Central. Java runtime загружен из официального Temurin-релиза и проверен по опубликованной SHA-256; provenance и лицензии находятся в `bin/jre/UPSTREAM.json` и `bin/jre/legal`. JAR содержит лицензии/NOTICE зависимостей и источник YouTube-модуля указан в vendor/UPSTREAM.txt.

Для разработки Java: Maven 3.9+ и Java 21, `bash scripts/build-engine.sh`. Скрипт записывает новый hash **после успешной сборки собственного артефакта**. Поменять hash постороннего повреждённого JAR для прохождения startup-проверки нельзя. Для обычной установки на Wispbyte Maven не нужен — готовый JAR включён. Автоматические Node-тесты: `npm run build` и `node --test dist/test/*.test.js`; Java-интеграция явно пропускается, если опциональный Linux runtime/артефакт не установлен.
